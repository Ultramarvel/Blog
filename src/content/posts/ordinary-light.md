## 为什么只看最终答案会被骗？

评估普通大模型时，我们很容易把注意力放在最终输出上，因为传统问答应用的核心产物就是一段文字：答案是否正确、是否相关、是否完整，基本就能反映系统质量。但 Agent 不一样。Agent 并不是直接从用户问题跳到最终答案，中间还存在一条完整的执行链：理解用户目标、判断下一步动作、选择工具、生成参数、读取工具返回结果、更新当前状态，再决定继续执行还是结束任务。只要其中任何一步出现问题，都可能让后续执行偏离正确方向。因此，Agent 的最终回答只能告诉我们“它最后说了什么”，却无法完整证明“它实际上做了什么”。

最典型的例子就是退款 Agent。假设三个 Agent 最后都回复用户“退款已经完成”，从文本层面看，它们几乎没有区别，但背后的行为可能完全不同。第一个 Agent 正确查询订单、核验用户身份、确认满足退款条件，然后调用退款接口并验证退款结果；第二个 Agent 根本没有调用退款接口，只是根据用户要求直接生成了一句“退款成功”；第三个 Agent 虽然真的调用接口完成了退款，却跳过了身份核验。三种情况的语言输出都可能非常自然，但只有第一种同时满足任务完成和流程合规要求。第二种属于“虚假完成”，第三种则可能直接造成安全事故。

因此，Agent 评估最重要的变化，就是不能再把模型自己的声明当作成功证明。真正可信的信号通常来自外部环境：退款任务应该检查订单和支付状态是否真的发生变化，创建日程应该检查日历里是否真正出现事件，修改代码应该运行测试验证，而不是因为 Agent 说“已经修改完成”就判定成功。Agent 评估本质上是在验证一个执行系统，而不仅仅是在评价一段自然语言。

## 四层评测，把问题定位到具体环节

一个比较实用的 Agent 评估体系，可以沿着 Agent 的执行链拆成四层：工具层、单步与轨迹层、端到端任务层以及线上业务层。这四层不是简单地多记录几个指标，而是在回答四个不同的问题：工具本身和调用方式可靠吗？Agent 每一步决策合理吗？整个任务最后真的完成了吗？上线以后，真实用户和业务是否真正受益？只有把这几个层次分开，出现失败以后才能快速定位到底应该修改工具实现、Prompt、模型能力、流程设计还是业务规则。

### 第一层：工具是否可靠

Agent 能完成任务的前提，是底层工具本身可靠。工具通常是相对确定的业务代码，因此应该优先通过传统软件测试方式验证，而不是一上来就把所有问题归因给大模型。比如一个退款工具需要先测试输入 Schema 是否正确、必填参数是否齐全、参数类型和取值范围是否合法，还需要覆盖正常返回、空结果、接口超时、权限不足和第三方系统异常等情况。对于支付、退款、发消息这类具有副作用的工具，还必须检查幂等性：同一个请求因为网络异常重复执行两次，不能真的扣款两次或者发送两条重复通知。

在工具本身可靠之后，再评估模型有没有正确使用工具。这里至少要区分两个问题：一是 Agent 有没有选对工具，二是选对工具之后参数有没有填对。例如模型知道应该调用 `refund_order`，说明工具选择正确，但如果订单号写错、退款金额超出订单金额，或者漏掉了必须的确认字段，调用仍然应该判失败。因此，工具层可以分别观察工具选择准确率、参数 Schema 通过率、参数语义正确率、工具执行成功率和重试后的成功率。

特别需要注意的是，Schema 通过只能证明 JSON 格式和字段类型合法，并不意味着参数的业务语义正确。一个订单号即使完全符合字符串格式，也可能属于另一个用户。

### 第二层：单步决策和完整轨迹是否合理

工具调用正确只是局部正确，Agent 还可能在流程上犯错。因此第二层要继续检查它的单步决策以及整条执行轨迹。单步评测通常是在一个固定状态下，把当前上下文交给 Agent，看它下一步是否做出了正确决定。例如当前缺少用户身份信息时，它应该继续调用退款工具，还是应该先追问用户？订单已经不存在时，它是应该停止任务，还是继续尝试后续操作？这类评测非常适合快速定位模型的决策边界问题。

轨迹评测则进一步检查完整执行过程。有些业务流程具有明确的顺序约束，例如退款必须先查询订单，再核验身份，满足条件以后才能执行退款。这种情况下，可以直接检查关键步骤的先后关系。但并不是所有任务都存在唯一正确轨迹。例如用户要求 Agent 搜集三个不同来源的信息，它既可以先搜索 A，再搜索 B，也可以交换顺序；如果不同信息彼此独立，就没有必要规定固定执行序列。

因此，轨迹评估最好不要简单准备一条所谓“标准轨迹”，然后要求 Agent 每一步完全匹配。更合理的方法，是为任务定义三类约束：哪些步骤必须出现，哪些行为绝对禁止，以及哪些步骤存在先后依赖。比如退款前必须完成身份验证属于“必须步骤”，未经授权读取其他用户订单属于“禁止动作”，而“身份验证必须发生在退款之前”属于“顺序依赖”。除此之外的执行路径可以保留一定自由度，这样才能兼顾 Agent 的自主性和业务安全。

轨迹层还应该关注效率。一个 Agent 最后虽然完成了任务，但如果反复查询同一个接口、频繁进入无意义的重试、调用大量与任务无关的工具，那么它依然不是一个好的 Agent。常见指标包括总步骤数、无效工具调用数、重复调用率、失败重试次数、Token 消耗和执行时间。

不过这里也不能简单迷信“步骤越少越好”。对于高风险任务，多进行一次身份核验或者状态确认，可能恰恰是正确设计。因此，轨迹效率应该建立在“任务成功且流程合规”的前提之上。

### 第三层：端到端任务是否真的完成

前两层关注过程，第三层真正回答“事情有没有办成”。端到端评测把 Agent 看成一个完整系统，从给定初始环境开始，让它独立执行整个任务，然后验证最终环境是否满足预先定义的成功条件。最直接的核心指标就是任务完成率，也就是成功达到目标状态的任务数量占全部评测任务的比例。

真正困难的地方并不是这个公式，而是如何定义“成功”。Agent 不能自己宣布成功，评估系统也不应该只检查最终回答是不是接近参考答案。只要存在客观环境状态，就应该优先验证客观状态。例如日历任务直接读取最终日程，退款任务检查订单和支付状态，代码任务运行自动化测试，文件编辑任务比较文件结果。只有像研究报告、分析文章、客服解释这种没有唯一结构化结果的开放式任务，才需要进一步根据事实正确性、完整性、相关性和可用性等 Rubric 进行评分。

对于复杂任务，只给最终结果一个 0 或 1 往往会损失大量诊断信息。假设一个 Agent 需要完成五个连续步骤，最后一步失败，那么从最终成功率看，它与第一步就失败的任务都记为 0，但两个系统的问题显然完全不同。因此可以额外记录阶段目标完成度，把任务拆成若干关键里程碑。这样不仅能知道任务有没有完成，还能看出 Agent 通常卡在哪一个阶段。

此外，Agent 具有随机性，因此端到端任务最好重复执行。同一个问题运行一次成功，并不能证明系统稳定。真正用于生产的 Agent 更关心同样条件下是否能够持续成功。可以对关键任务重复执行多次，观察稳定成功率，而不是只报告一轮测试结果。这里的核心思想很简单：测试的不是“模型有没有可能完成这个任务”，而是“模型能不能稳定地完成这个任务”。

### 第四层：线上业务是否真的得到改善

即使 Agent 在离线评测集上表现优秀，也不代表真实用户一定满意。评测集永远只能覆盖有限场景，而线上环境会不断出现新的表达方式、新的工具状态和新的边界情况。因此 Agent 上线以后，还需要继续观察业务指标和工程指标。

业务层面可以关注任务解决率、人工接管率、用户纠正率、撤销率、重复尝试率，以及真正的业务结果。例如客服 Agent 的目标并不是让用户对回复点赞，而是最终问题有没有解决；编程 Agent 的目标也不只是生成代码，而是修改是否被接受、测试是否通过。用户反馈非常有价值，但只能作为代理指标，不能完全代替真实业务结果。

工程指标同样重要。Agent 可能任务成功率很高，但一次任务需要几十轮模型调用，成本和延迟可能完全无法接受。因此需要记录成功任务的平均 Token 消耗、模型调用次数、工具成本、端到端延迟以及不同分位的响应时间，同时关注工具超时、异常退出和重试情况。

尤其是安全指标必须单独统计，比如未授权工具调用率、敏感数据泄露率、提示词注入攻击成功率和审批流程绕过率。这些指标不能因为总体任务完成率很高，就被放进一个综合分中互相抵消。

## 小结
评估 Agent，不能只盯着最终答案，而要沿着它的执行链逐层判断：工具有没有选对、参数有没有填对，单步决策和完整轨迹是否合理，最终任务是否真正完成，以及上线后是否真的带来更好的业务结果。尤其对于退款、支付、审批这类高风险任务，成功不只是“事情做成了”，还必须保证过程合规、权限正确、结果可验证。一个成熟的 Agent 评测体系，本质上是在回答三个问题：它有没有做对、是不是用正确的方式做对，以及能不能稳定、安全、低成本地持续做对。
